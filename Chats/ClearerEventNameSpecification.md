# Clearer Event Name Specification

## Bruce's Ask

I *think* we have a few consistent patterns as far as specifying the event name:

[do-inc](https://github.com/bahrus/do-inc#specifying-the-event-to-trigger-increment)

```html
<mood-stone itemscope>
    <span itemprop=age></span>
    <button name=age  ➕="byAmt `12` on mouseover">Increment</button>
</mood-stone>
```

[be-switched](https://github.com/bahrus/be-switched#specifying-event-names)

```html
<ways-of-science itemscope>
    <carrot-nosed-woman #></carrot-nosed-woman>
    <a-duck #></a-duck>
    <data  defer-🎚️
        🎚️="on per #{{carrot-nosed-woman}}@weight-change and #{{a-duck}}@molting"
        onchange="event.r = Math.abs(event.f.carrotNosedWoman - event.f.aDuck) < 10"
    ></data>
    <div>A witch!</div>
    <div -id>Burn her!</div>
    
</ways-of-science>
```

How difficult would it be to support both and drop support for ::?  Do not incur any technical debt whatsoever by providing any backwards compatibility support.

If more clarification needed, please continue the discussion below.  If not, please implement, and add your implementation notes below.

## Implementation Notes

### Status

Done. `npm run build` regenerates both JSON configs; `npm run test` is green
(4 Playwright specs — the 3 existing ones plus a new `EventNameOnClause` that
exercises the `do-inc`-style trailing clause). No backwards-compat shim of any
kind — the `::` form now simply fails to parse.

### What "support both" turned into

`be-persistent` only ever deals with a **local** property/event on the enhanced
element itself (no `#{{elementRef}}` indirection), so the two sibling grammars
collapse to two spellings of the same thing:

| Style | Borrowed from | Example |
|-------|---------------|---------|
| `@<event>` glued to the property | [`be-switched`](https://github.com/bahrus/be-switched#specifying-event-names) (`#{{a-duck}}@molting`) | `of value@change via sessionStorage://{autoGenId}` |
| trailing `on <event>` clause | [`do-inc`](https://github.com/bahrus/do-inc#specifying-the-event-to-trigger-increment) (`byAmt \`12\` on mouseover`) | `of value via sessionStorage://{autoGenId} on change` |

Both are optional; when neither is present the event still defaults to `input`
(unchanged, still applied in `Binder`, not via a parser `defaultVal`).

### The grammar (in `emc.mjs`, the source of truth)

Five `PatternConfig` entries, most-specific first, replacing the previous three:

```
of <prop>@<event> via <usl>          ofLocalPropAtLocalEventViaUSL
of <prop> via <usl> on <event>       ofLocalPropViaUSLOnLocalEvent
of <prop> via <usl>                  ofLocalPropViaUSL
via <usl> on <event>                 viaUSLOnLocalEvent
via <usl>                            viaUSL
```

- Event group widened from `\w+` to `[\w-]+` so hyphenated names
  (`weight-change`, `my-custom-event`) parse — matching what `do-inc` /
  `be-switched` already accept.
- `<usl>` stays `\S+`; the ` on ` in the trailing clause has surrounding spaces
  so it can never be swallowed by the USL.
- Ordering matters: the `...OnLocalEvent` variants precede their plain
  counterparts, otherwise `\S+$` in the plain rule would never let the `on`
  clause be reached (it wouldn't actually mis-match — the `$` anchor fails on
  the space — but keeping specific-first is the established convention here).

### Dropping `::` with zero debt

`localProp` was `[\w:]+` (the colon was there precisely to feed the `::`
splitter). It is now `[\w]+`. Consequence: a leftover `of value::input via …`
statement matches **no** pattern — the parser reports
`No pattern matched input: "of value::input via …"`, that statement is dropped,
and (if it was the only statement) `hydrate` falls back to the default rule.
No silent re-interpretation of `value::input` as a bogus property name, and no
alias/deprecation path.

### Follow-up worth noting

The existing specs prove the value **round-trips at init time**; none of them
actually dispatch the configured event, so the new `EventNameOnClause` spec
locks in that the grammar *parses* but doesn't independently verify a non-default
event firing. A spec that wires `@keyup` (or `on keyup`) and dispatches a real
`keyup` would close that gap — same follow-up already flagged in `Conversion.md`
note 4 about adopting `infer`.
